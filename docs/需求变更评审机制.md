# AutoClicker 需求变更评审机制

> 对应 PRD §1.5 / T05278。范围：PRD §2.3「非目标（明确不做）」以及已冻结的范围边界。本文是流程文件，不是代码功能。

## 1. 目的

防止「录制回放/图像识别/反检测」等 §2.3 非目标或已冻结范围被单个需求、口头指令或实现顺手扩大，导致 P0 稳定性和交付节奏被拖慢。所有越界变更必须先评审、后实施。

## 2. 适用范围

以下任一情形必须走本机制：

1. 新增 PRD §2.3 明列的非目标能力（反检测/反作弊、进程注入/内存修改/驱动隐藏、无提示静默点击、全功能脚本引擎）。
2. 把「录制回放」从「点击 + 按键 + 延时」最小集扩展到图像识别、条件分支、循环、变量、网络请求等。
3. 改变已冻结的交付范围、验收口径、平台矩阵或安全边界（如新增远控、上传、自动更新通道）。
4. 为绕过已有关闭项而采用的等价实现（换名称、换入口、默认开启等）。

## 3. 角色与职责

| 角色 | 职责 |
|---|---|
| 需求提出人 | 提交变更单，说明场景、收益、不做的后果 |
| 产品/项目负责人 | 判定是否属于 §2.3、决定是否受理、最终拍板 |
| 技术负责人 | 评估实现路径、依赖、回归范围、工期与风险 |
| 测试/安全 | 评估验证成本、安全合规与平台兼容风险 |
| 记录人 | 把结论写回 MTask，维护变更台账 |

小团队可一人兼多角色，但「提出」和「拍板」不能是同一人。

## 4. 变更单模板（最小字段）

```text
变更标题：
提出人 / 日期：
关联 PRD 条目：§2.3-N / FR-xxx / NFR-xxx
现状与动机（为什么现在必须做）：
不做的影响（用户/业务/合规）：
建议范围（明确不包含什么）：
实现与依赖：
工期 / 资源：
风险（安全/兼容/回归/维护）：
验证方案（真机/命令链/文档）：
```

## 5. 评审流程

1. **提交**：在 MTask 建立变更任务，标题带 `【变更评审】`，描述使用上表字段；不得直接改代码。
2. **预审（1 个工作日）**：产品负责人判断是否属于 §2.3。属于则进入正式评审；不属于则转为普通需求并补充验收口径。
3. **技术评估（1~2 个工作日）**：技术负责人给出实现方案、影响文件、回归范围、工期；涉及打包/平台矩阵时同步评估 PyInstaller 体积、麒麟/arm64 兼容。
4. **评审会（不超过 30 分钟）**：逐项确认「做/不做/延后」，形成明确结论；未达成一致由产品负责人拍板。
5. **记录**：结论写回 MTask 变更任务，并在 PRD §2.3 或范围章节追加「解冻记录」；未记录视为未批准。
6. **实施**：批准后才可建开发任务；开发任务描述必须引用变更单编号，验收必须覆盖变更单中的验证方案。
7. **复审**：上线/发版前由测试确认实现未超出批准范围；超范围按新变更重新评审。

## 6. 决策口径

- **接受（Accept）**：进入范围，更新 PRD、排期、验收与风险登记。
- **延后（Defer）**：方向可行但当前不做；记录触发条件（如「V2.3 后」「有企业客户合同要求」）。
- **拒绝（Reject）**：违反 §2.3 或安全/合规底线；写明理由与替代方案。
- **降级（Downgrade）**：只做最小子集，明确不做的部分。

默认结论是「不做」；没有明确 Accept 记录不得实施。

## 7. 解冻记录格式

在 PRD 非目标条目后追加：

```text
> 解冻记录：<变更单 Txxxx> / <日期> / <结论> / <批准范围> / <批准人>
```

只有带批准范围的条目才解除对应限制；其余部分仍然冻结。

## 8. 与 MTask 的衔接

- 变更单：`【变更评审】<标题>`，`status=todo`，不直接进开发。
- 批准后派生开发单：`derivedFrom=<变更单>`，描述引用批准范围。
- 拒绝/延后单保持 `done` 并写结论，不归档到不可见状态。
- 台账按季度导出一次，随版本发布记录归档。

## 10. 生效与复审

- 生效日期：2026-11-16。
- 复审周期：每季度或每次范围变更后 5 个工作日内。
- 本文与 PRD §2.3 冲突时，以 PRD 原文为准；流程解释权归产品负责人。
