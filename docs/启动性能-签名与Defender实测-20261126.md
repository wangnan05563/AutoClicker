# 启动性能：签名产物与 Defender 实测（T06328）

实测时间：2026-11-26 00:35–01:10（CST）
结论先行：**Defender 实时扫描是主要拖慢项之一，但不是唯一原因；临时自签名产物没有改善启动，不能作为 AC-16 的解决方案。**

## 结论

1. **Defender 进程级排除把未签名产物中位数从 19.763s 降到 4.971s，减少 14.792s（74.8%）**。这直接证明 Defender 对该进程的实时检查是 15–20s 启动延迟的主要来源。
2. **排除后仍未达到 AC-16 <3s**：最好样本 3.982s，中位数 4.971s；相对源码 `TOTAL=2.73s`，PyInstaller onedir 运行时仍有约 2.2s 固定开销。
3. **自签名没有帮助**：84 个 PE 全部签名后，普通 Defender 环境下中位数 25.433s，反而比未签名暖启动的 19.763s 慢 5.670s；进程排除后签名产物中位数 7.137s，也比未签名的 4.971s 慢 2.166s。自签名证书链校验和未知发布者状态引入了额外开销，且**不能代表真实 OV/EV 或 Trusted Signing 证书**。
4. 本机 `MsMpEng` 在空闲期仍持续占用 86%–202% 单核 CPU，环境本身存在后台扫描，绝对数值有噪声；因此本轮只能确认“扫描是主要贡献项”，不能给出干净的绝对值基线。

## 判定

**是主因之一，但不是唯一原因。**

- Defender 实时扫描贡献了约 14.8s 的启动延迟；这与此前首次启动 57.9s、后续 7–8s 的模式一致。
- 即使完全绕过 Defender 对该进程的扫描，仍有 4–5s 启动时间；这部分来自 PyInstaller onedir 加载、Python 运行时初始化和应用初始化，单靠签名/加白无法压到 3s。
- 临时自签名不仅没有减少扫描，反而增加约 2s；真实证书可能改善 SmartScreen 和发布者信誉，但不能假定它会减少 Defender 实时扫描。
- 本机 Defender 持续后台占用，且源码目录已被排除，当前数据只能作趋势判定，不能作为最终验收基线。

## 下一步建议

1. **先取得真实代码签名能力**：OV/EV 证书或 Microsoft Trusted Signing，在干净的 Windows VM 上对比“未签名 / 已签名”在 Defender 实时保护开启下的首次与暖启动。没有真实证书前，不再重复自签名测试。
2. **同时处理 4–5s 的运行时底座**：在进程排除条件下做启动埋点，拆分 PyInstaller 引导、Python 导入、Tk 初始化、应用初始化，确认剩余 2.2s 的具体归属；不要回到 Tcl 数据裁剪。
3. **AC-16 口径需要澄清**：如果验收环境本身带持续 Defender 扫描，3s 目标在 onedir 下不可达；应将“首次启动 AV 扫描”与“暖启动”分开定义，或明确要求部署侧排除/白名单。
4. 暂不把 T06328 标 done；本轮只完成“签名 + Defender 归因”，未完成性能达标。
